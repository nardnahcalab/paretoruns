Entropy measures routing diversity: Where pi is the fraction of tokens routed to expert i, and K is the number of experts. Normalized so 1.0 = perfectly uniform distribution across all experts. Higher entropy = more evenly distributed tokens.

What entropy does NOT tell you

Not a performance predictor

TTFT and decode throughput show no strong correlation with entropy. Differences across datasets (entropy 0.76-0.79) correspond to < 5% performance variation — within noise.

Not a quality indicator

Entropy doesn't tell you if the model is "good" — it only describes how tokens are distributed. Both focused and diverse routing can produce high-quality outputs.

Provision = Ideal_Uniform × (1 / Entropy_Normalized) × Safety_Margin

4. Why Imbalance Exists Despite High Entropy

Entropy is an average

Entropy averages across all tokens. Even with high average diversity, individual tokens still concentrate on a few experts. The variance in expert selection matters more than the mean.

Top-K creates concentration

With Top-8 routing, each token picks 8 experts. But "picking" doesn't mean equal load — some experts are preferred by many tokens, creating hot spots.

Content similarity

Tokens from similar contexts (e.g., same language, same topic) tend to route to similar experts. This creates load spikes even with diverse routing overall.

Layer variation

Different layers have different entropy (0.70-0.86). Layers with lower entropy concentrate more tokens on fewer experts, creating per-layer hot spots.

6. Practical Recommendations

For GPU Memory Allocation

Don't size for average — size for hot experts.
  • If average expert needs 2GB, provision 40GB for the hot expert
  • Monitor per-expert memory usage, not just total GPU utilization
  • Consider expert offloading for cold experts (30-40% are idle)

For Compute Scheduling

Batch composition matters less than expected.
  • Entropy is content-agnostic — text, random, and reasoning produce similar routing
  • No need to separate workloads by type for routing efficiency
  • Focus scheduling on batch size optimization, not content filtering

For Cost Optimization

What works

  • Increase batch size to amortize hot expert overhead
  • Use NVFP4 for 4x memory savings without routing degradation
  • Monitor Gini coefficient to track imbalance trends

What doesn't work

  • Optimizing batch composition by content type
  • Expecting entropy to predict latency
  • Provisioning for average expert load

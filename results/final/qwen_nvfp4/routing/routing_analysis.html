H = −Σ(pi × log2(pi)) / log2(K)

Where pi is the fraction of tokens routed to expert i, and K = 256 (total experts). Normalized so that 1.0 = perfectly uniform routing across all experts, and 0.0 = all tokens routed to a single expert. With top-8 routing (3.1% of experts active per token), a perfectly balanced router would give entropy close to 1.0.

1. What Is Routing Entropy?

Entropy measures how evenly tokens are distributed across experts. A perfectly uniform distribution (every expert gets 1/256 of tokens) gives entropy = 1.0. A distribution where one expert gets all tokens gives entropy = 0. Higher entropy = more diverse routing. The formula: H = -Σ(p_i × log₂(p_i)) / log₂(K) where p_i is the fraction of tokens routed to expert i, and K is the number of experts. Normalized by log₂(K) so 1.0 = max diversity.

Glossary

Prefill
The initial phase where the model processes the input prompt. All input tokens are processed in parallel. Determines how fast the model "understands" the request.
Decode
The phase where the model generates output tokens one at a time. Each new token requires a forward pass. Determines output speed and throughput.
TTFT (Time to First Token)
Latency from request submission to first output token. Primarily determined by prefill speed. Lower is better for interactive applications.
Throughput
Tokens generated per second. Higher is better. Affected by batch size, model efficiency, and hardware.
Top-K Routing
Each token is sent to the K highest-scoring experts. Here K=8 out of 256, meaning 3.1% of experts are active per token.
Expert Load Balance
How evenly tokens are distributed across experts. Imbalanced load causes some experts to be underutilized while others become bottlenecks.

5. NVFP4 Quantization Impact

Memory Efficiency

NVFP4 uses 4-bit precision, reducing memory by 4x compared to bf16. This enables the 35B model to fit on GB10's 128GB unified memory with room for large context windows.

Routing Stability

The router's gate computation uses 4-bit activations, which may introduce quantization noise. However, the entropy patterns (0.76-0.85) are stable across datasets, suggesting the router is robust to precision loss.

Throughput Trade-off

NVFP4 enables higher throughput (more tokens/second) at the cost of minor quality degradation. The routing patterns suggest the model maintains its MoE behavior well under quantization.

Comparison to FP8

FP8 (8-bit) would show slightly more stable routing but use 2x more memory. The NVFP4 routing entropy (~0.76-0.85) is comparable to typical FP8 MoE models, indicating minimal routing degradation from quantization.

6. Research Findings

Content-Agnostic Router

The router doesn't dramatically change behavior based on input type. Text, random, and reasoning inputs all produce entropy in the 0.76-0.85 range. The router routes based on token-level patterns, not task semantics.

Strong Position Effect

Entropy increases 6-12% from early to late positions. This is stronger than Nemotron's 3-5%, suggesting Qwen's pure MoE architecture has more routing flexibility without Mamba layers constraining the distribution.

Moderate Load Imbalance

The top expert captures ~8% of tokens (vs 3.1% ideal for 256 experts with top-8). This indicates moderate load imbalance but no extreme hotspots — the router maintains reasonable expert utilization.

Layer Variation

Entropy varies across layers (0.70-0.86), with early layers showing higher entropy and middle layers showing lower entropy. This suggests different layers specialize in different routing patterns.

8. Routing Entropy at Scale: Expert Parallelism

Scaling MoE models beyond a single GPU requires Expert Parallelism (EP) — distributing the 256 experts across multiple GPUs so each device hosts a subset. The routing entropy and load distribution measured in this probe directly determine how efficiently EP can operate.

What Is Expert Parallelism?

Single-GPU (This Probe)

All 256 experts reside on one GPU. The router selects 8 experts per token, and the MoE kernel processes them sequentially or in small batches on the same device. No inter-device communication.

This is how Qwen NVFP4 runs on the Dell Pro Max with NVIDIA GB10 — single GPU, tensor-parallel-size 1.

Expert Parallel (Multi-GPU)

Experts are sharded across N GPUs (e.g., 256 experts / 32 GPUs = 8 experts per GPU). Each token's selected experts may live on different GPUs, requiring all-to-all communication to dispatch tokens to the right device and collect results.

The All-to-All Communication Pattern

Every MoE layer triggers two all-to-all collectives per forward pass:
  1. Dispatch: Each GPU sends tokens to the GPU(s) owning their selected experts. A token routed to expert 42 (on GPU 5) physically travels to GPU 5.
  2. Compute: Each GPU processes only tokens destined for its local experts.
  3. Combine: Results are sent back to originating GPUs, weighted by gating scores.
With 40 MoE layers in Qwen3.6, this means 80 all-to-all collectives per forward pass. At high concurrency, this communication dominates execution time.

How Entropy Determines EP Efficiency

Low Entropy (Peaked Routing)

Problem: A few experts receive most tokens. GPUs hosting these hot experts become bottlenecks — the entire EP group waits for the slowest device.

Measured: Qwen NVFP4 top expert captures 8% of tokens (vs 3.1% ideal). Hot experts receive 8-23x more tokens than uniform distribution.

Hi-repeated: Entropy drops to 0.474 at early layers (49.5% lower than text). Repetitive inputs create extreme hotspots with 30-50x imbalance.

High Entropy (Spread Routing)

Benefit: Tokens distribute more evenly across experts. All GPUs process similar token counts → balanced utilization, higher throughput, better all-to-all traffic patterns.

Measured: Multi-turn entropy reaches 0.855 (text) — better EP efficiency for longer sequences with diverse routing.

Layer Variation Effect

Complication: Entropy varies by layer (0.70-0.86). Lower-entropy layers create per-layer hot spots even when overall entropy is high. EP must be provisioned for the worst-case layer, not the average.

The Two-Regime Problem

Reality: In any production batch, hot experts sit in the compute-bound regime (weight loading dominates) while cold experts sit in the memory-bound regime (activation floor dominates). 92-100% of batches contain both regimes simultaneously.

Worked example for EP=32 deployment:

  • At 128 concurrent requests × 512 tokens = 65,536 tokens
  • Ideal per expert: 2,048 tokens (65,536 × 8 / 256)

  • HI-REPEATED scenario: entropy 0.627 → up to 35x imbalance, requiring 4-5x more memory headroom per GPU
Recommendation: Size memory for the worst-case layer (layer 30: 22.9x ratio), not the average. For repetitive workloads, provision for 35x imbalance. Use expert replication or dynamic load balancing to mitigate hot spots.

Production Deployment Strategies

Expert Replication

Create redundant copies of hot experts and distribute tokens across replicas. This trades memory for balance — each hot expert replica consumes memory on additional GPUs but reduces the bottleneck.

For Qwen NVFP4: replicate experts that appear in the top-14% (hot experts) across 2-3 GPUs.

Dynamic Load Balancing

Monitor per-expert token counts at runtime and rebalance by migrating experts between GPUs or adjusting dispatch weights. Systems like EPLB and METRO reduce decode latency by 11-22%.

Cross-Layer Scheduling

Use experts from other layers as "natural redundancy" — jointly execute workloads from multiple layers to mitigate per-layer imbalance. Reduces GPU idling by 40%+ with zero extra memory.

Adaptive Top-K (GeMoE)

High-entropy tokens get more experts (better quality), low-entropy tokens get fewer (saves compute). Achieves 99.5% quality retention with 36.5% fewer expert activations — simultaneously improving quality and system balance.

When Wide EP Helps (and When It Doesn't)

Wide EP Benefits

  • Reduced weight-loading overhead per GPU (fewer experts per device)
  • Larger local token batches per expert → higher GEMM efficiency
  • 1.8x per-GPU throughput improvement on GB200 NVL72
  • Best for models with 256+ experts where weight loading dominates

Wide EP Limitations

  • Requires massive aggregate bandwidth (NVL72: 130 TB/s)
  • All-to-all communication increases with more GPUs
  • Smaller MoE models gain little — communication outweighs benefits
  • Routing entropy still determines balance quality within the EP group
Bottom line for Qwen NVFP4 on GB10: This probe was run on a single GPU (EP=1). Scaling to multi-GPU deployments requires addressing the 8-23x load imbalance measured across layers. The content-agnostic routing (similar entropy across text/random/reasoning) means batch composition won't help — focus on expert replication, dynamic balancing, and provisioning for the worst-case layer (30-40% cold experts, 22.9x hot expert ratio). For HI-REPEATED workloads (automated systems, chatbot retries), provision for 35x imbalance and consider input preprocessing to diversify repetitive prompts.

10. Why Entropy Is Similar Despite Different Routing

The paradox: The router selects nearly disjoint expert sets for different content (Section 9), yet the entropy (distribution shape) is nearly identical across text/random/reasoning. The Hi-repeated dataset breaks this pattern — with entropy 0.627 (25.9% lower), it proves that vocabulary diversity directly affects routing diversity. This reveals what entropy actually measures: it's sensitive to both which experts and how concentrated the load is.

Entropy Measures Shape, Not Identity

What Entropy Measures

Entropy answers: "How concentrated is the distribution?" It doesn't care which experts are hot — only how many experts are hot and how hot they are. Two distributions with identical Gini coefficients can have completely different expert assignments.

Analogy

Two cities can have identical income inequality (Gini = 0.7) even though different people are rich. Similarly, text and random can have identical routing entropy even though different experts are loaded.

Why the Similarity Exists

1. Training Regularization

The auxiliary load-balancing loss during training penalizes extreme concentration. It pushes ALL routing distributions toward the same shape, regardless of content. The router learns which experts for what, but the spread is regularized to be uniform.

2. Top-8 Structural Constraint

With 256 experts and top-8 routing, each token activates exactly 3.1% of experts. This mechanical constraint limits how different entropy can be — the distribution is bounded by K/N regardless of content.

3. Short Decode Sequences

The single-turn probe captures only 8 decode tokens — the model barely starts generating. Content-specific routing patterns need longer sequences to emerge. The multi-turn probe (64 tokens) shows slightly more differentiation (random 3.4% lower entropy).

4. The Router is Content-Agnostic in Diversity

The training objective doesn't reward content-dependent diversity — it rewards balanced load. The router optimizes for which experts handle what content, not for how differently to spread tokens. Entropy similarity is a feature, not a bug.

5. Hi-Repeated Breaks the Pattern

Replacing all words with "hi" reduces entropy by 25.9% (0.846→0.627). This proves the router IS sensitive to vocabulary diversity — but only when diversity drops below a threshold. Natural language types (text/random/reasoning) all have sufficient diversity to maintain similar entropy shapes.

What This Means for Deployment

Entropy is not the right metric for predicting content-dependent behavior. Instead, monitor:
  • Expert overlap (Jaccard): Measures whether different content uses different experts — useful for caching, expert pre-loading, and content-aware scheduling
  • Cosine similarity of load vectors: Measures how similarly all 256 experts are loaded across datasets — useful for capacity planning across mixed workloads
  • Per-layer divergence: Some layers (20, 23, 35) show maximum divergence — these are the layers where content-aware routing is most active
  • Vocabulary diversity: Hi-repeated shows 25.9% entropy reduction — monitor input diversity for automated/retry workloads to prevent expert hotspots

Implications for Infrastructure

Load Balancing Risk

Repetitive inputs (common in automated systems, chatbots, or retry scenarios) create hotspot experts that receive disproportionate traffic. This can lead to:

  • Uneven GPU memory utilization
  • Increased latency for hotspot expert computations
  • Potential OOM if hotspots exceed memory capacity

Mitigation Strategies

  • Input diversification: Add random padding or paraphrasing
  • Expert capacity planning: Size for 2x average load
  • Dynamic routing: Implement load-aware routing if available
  • Monitoring: Track per-expert utilization in production
Action Items:
  1. Monitor per-expert load in production for repetitive input patterns
  2. Implement input preprocessing to diversify repetitive prompts
  3. Size GPU memory for worst-case expert hotspots (2x average)
  4. Consider dynamic routing adjustments for high-repetition workloads

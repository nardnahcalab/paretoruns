1. Overview & Motivation

Mixture-of-Experts models route each token through a subset of "experts" in every MoE layer. The routing decision depends on the token's learned representation, which in turn depends on the type of content being processed. This means:

  • Natural text has strong token correlations (word bigrams, grammar, semantics) that shape how experts are selected.
  • Random words break all correlations, forcing the router to activate a different mix of experts on every token.
  • Reasoning chains create deep, structured attention patterns where each token depends on prior logical steps.

By benchmarking all three workloads against the same model and hardware, we can observe how the MOE architecture's routing behavior manifests as measurable differences in prefill latency (TTFT), decode throughput (tok/s), inter-token latency (ITL), and GPU utilization.

The two scripts in this project automate the full pipeline: launch_vllm.sh deploys the model, and run_benchmark.sh sweeps concurrency levels across all three datasets, collecting GPU telemetry and generating Pareto frontier plots.

3. MOE Model: Qwen3.6-35B-A3B

Two quantized variants benchmarked on GB10: nvidia/Qwen3.6-35B-A3B-NVFP4 (4-bit MoE, primary baseline) and Qwen/Qwen3.6-35B-A3B-FP8 (8-bit MoE, comparison).

PropertyValue
Total Parameters35B
Active Parameters3B per token
Experts256 total, 8 routed + 1 shared
ArchitectureGated DeltaNet + MoE hybrid (linear attention + softmax attention)
Layers40 (10 Gated Attention + 30 Gated DeltaNet)
QuantizationNVFP4 (ModelOpt) — MoE experts in 4-bit, attention projections in FP8
Context Length262,144 tokens native, extensible to 1M via YaRN
MTP SupportMulti-Token Prediction trained

Why This Model

The 256-expert / 8-active architecture means only ~3% of parameters execute per token. The router must choose which 8 experts to activate, and this choice is content-dependent. Text, random, and reasoning inputs produce measurably different routing distributions, which in turn affect:

  • Prefill speed — expert selection affects compute distribution across SMs
  • Decode throughput — router efficiency directly impacts tokens/second
  • Memory pressure — different experts being active means different weight pages in VRAM

All three datasets are isomorphic: identical session count, turn count, and word count. Only the content differs.

JSONL Format

Each line is a self-contained multi-turn session:

{"session_id": "...", "turns": [{"text": "How can I improve my sleep quality?"}, {"text": "Can you give me a specific example?"}]}

AIPerf's --custom-dataset-type multi_turn loader reads these files. Each turn is sent sequentially within a session, with the full conversation history accumulated. Multiple sessions run concurrently up to the --concurrency limit.

6. Script: launch_vllm.sh

Deploys the MOE model in a Docker container with GB10-specific settings. Handles preflight checks, container lifecycle, health verification, and a quick sanity test.

Usage

# Start server (default: NVFP4)
./launch_vllm.sh

# FP8 model (requires --load-format safetensors --enforce-eager)
./launch_vllm.sh --model Qwen/Qwen3.6-35B-A3B-FP8 --load-format safetensors --enforce-eager

# Custom model and port
./launch_vllm.sh --model nvidia/Qwen3.6-35B-A3B-NVFP4 --port 8000

# More aggressive memory usage
./launch_vllm.sh --gpu-mem 0.5 --max-seqs 8

# Check status
./launch_vllm.sh --status

# Stop server
./launch_vllm.sh --stop

Options Reference

FlagDefaultDescription
--model MODEL nvidia/Qwen3.6-35B-A3B-NVFP4 HuggingFace model ID. The NVFP4 checkpoint ships with 4-bit MoE experts and FP8 attention projections.
--port PORT 8000 Host port for the OpenAI-compatible API endpoint.
--gpu-mem UTIL 0.4 Fraction of GPU-visible memory vLLM may claim. On GB10 this is a fraction of the unified pool. Keep under 0.5 for long-context workloads; OS and page cache compete for the same 128 GB.

--image IMAGE vllm/vllm-openai:v0.24.0-ubuntu2404 vLLM Docker image. Must support aarch64/SM121. The default is the official vLLM image with GB10 support.
--name NAME vllm-moe-gb10 Docker container name. Used for --stop and --status commands.
--stop — Force-remove the container. Weight and compile caches on mounted volumes survive.
--status — Show container state, health check result, and registered model list.

8. Why MOE Performance Differs by Dataset

Expert Routing in MOE

In each MoE layer, a router network (typically a learned linear projection + softmax) assigns each token to the top-K experts. For Qwen3.6-35B-A3B, K=8 out of 256 experts. The router's decision is based on the token's hidden state, which is shaped by all preceding tokens.

Dataset-Specific Behavior

Text Dataset

  • Token correlations: Natural English has strong bigram/trigram statistics. The router sees familiar patterns and selects a consistent expert mix across similar contexts.
  • Prefill: Moderate TTFT. Prefix caching is effective because conversation turns share common framing ("How can I...", "Can you...").
  • Decode: Highest throughput. Predictable token patterns let the model pipeline expert computation efficiently.
  • GPU utilization: Balanced across SMs since expert selection is distributed.

Random Dataset

  • Token correlations: None. Every token is semantically unrelated to its neighbors. The router sees a different "topic" on every token.
  • Prefill: Higher TTFT than text. The router must evaluate all 256 experts more evenly since there's no pattern to exploit.
  • Decode: Lower throughput. Each decode step requires full router evaluation with no prediction benefit from prior tokens.
  • GPU utilization: May show higher variance across SMs as different expert combinations are activated per token.

Reasoning Dataset

  • Token correlations: Deep logical structure. Each token depends on reasoning chain built in prior tokens ("Assume X, therefore Y, which implies Z...").
  • Prefill: Potentially fastest. Reasoning prompts are formulaic and shorter ("Prove that...", "Show every step..."). Less text to process.
  • Decode: Highest ITL (inter-token latency). Each output token requires attending to the full reasoning chain. The model cannot "shortcut" logical dependencies.
  • GPU utilization: Concentrated on attention-heavy experts during chain-of-thought generation.

Prefix Caching Interaction

Prefix caching (--enable-prefix-caching) interacts differently with each dataset:

  • Text: Moderate benefit. Turn prefixes overlap in phrasing but diverge in content.
  • Random: Minimal benefit. Random words produce different token sequences each time, so KV cache reuse is limited.
  • Reasoning: Maximum benefit. System prompts and formulaic opening phrases form long shared prefixes across sessions.

9. Reading the Pareto Curves

AIPerf's pareto plot shows Throughput vs Latency (or TTFT vs Throughput) with the Pareto frontier highlighted. Each data point represents one concurrency level. The three datasets should produce distinct curves:

Interpreting the Curves

Curve ShapeMeaning
Steep ascent (throughput rises fast with concurrency) Good scalability. The MOE router handles increased load efficiently. Expected for text dataset.
Flat or declining at high concurrency Bottleneck reached. Memory bandwidth (273 GB/s) or KV cache saturation limits further gains. Expected at concurrency ≥8 on GB10.
Higher baseline latency but steep curve Expensive prefill but good decode scaling. Expected for reasoning (deep attention chains).
Lower throughput at all concurrency levels Router inefficiency. Random content prevents the model from exploiting token patterns. Expected for random dataset.
Different frontier positions per dataset MOE routing sensitivity to content type. This is the core finding this benchmark aims to produce.

Key Metrics to Compare

MetricWhat It ShowsExpected Ordering
TTFT (Time to First Token) Prefill latency. How long until the first output token arrives. random ≥ text > reasoning (shorter prompts)
ITL (Inter-Token Latency) Decode speed. Time between consecutive output tokens. reasoning > random > text
Throughput (tok/s) Decode throughput. Total tokens generated per second. text > random > reasoning
GPU Utilization % How much of the GPU is busy. Low utilization = bottleneck elsewhere. text ≥ reasoning > random
Request Latency P99 Worst-case total request time. Includes prefill + decode + overhead. reasoning > random > text

10. Quick Start

Prerequisites

  • NVIDIA GB10 (DGX Spark) with Docker and nvidia-container-toolkit
  • HuggingFace token: export HF_TOKEN=hf_your_token_here
  • ~45 GB free disk for model weights (~35 GB) + container image (~10 GB)

Step 1: Launch the Server

cd pareto/
export HF_TOKEN=hf_your_token_here

# NVFP4 (default, recommended for multi-user)
./launch_vllm.sh

# FP8 (faster for single-user, requires extra flags)
./launch_vllm.sh --model Qwen/Qwen3.6-35B-A3B-FP8 --load-format safetensors --enforce-eager

First boot downloads the model (~35-37 GB) and compiles CUDA graphs (NVFP4 only). Allow 15-25 minutes. Subsequent starts use cached weights and are much faster. FP8 first boot takes ~30 min due to safetensors loading (no fastsafetensors).

Step 2: Run the Benchmark

./run_benchmark.sh

Runs 12 benchmark runs (3 datasets × 4 concurrency levels) with GPU telemetry, then generates a pareto_report.html via make_pareto.py. Total time: 20-40 minutes.

Step 2b: Additional Sweeps

# Long decode-phase outputs (reveals content-type routing differences)
./run_sweep.sh --concurrency '1 2' --output-tokens 512 --output-std 128 --requests 50 --label longtok

# Fill the 512-tok gap at c4,c8
./run_sweep.sh --concurrency '4 8' --output-tokens 512 --output-std 128 --requests 50 --label longtok_gap

# Find the concurrency saturation point (128-tok)
./run_sweep.sh --concurrency '16 32' --output-tokens 128 --output-std 32 --requests 60 --label sat

# High-confidence sweep (200 requests for tighter CIs)
./run_sweep.sh --concurrency '1 2 4 8' --output-tokens 128 --output-std 32 --requests 200 --label highconf

# Long-output saturation (512-tok at high concurrency)
./run_sweep.sh --concurrency '16 32' --output-tokens 512 --output-std 128 --requests 60 --label longtok_sat

# FP8 comparison sweeps (requires FP8 server running)
MODEL_NAME=Qwen/Qwen3.6-35B-A3B-FP8 ./run_sweep.sh --concurrency '1 2 4 8' \
  --output-tokens 128 --output-std 32 --requests 200 --label fp8_128

MODEL_NAME=Qwen/Qwen3.6-35B-A3B-FP8 ./run_sweep.sh --concurrency '1 2 4 8' \
  --output-tokens 512 --output-std 128 --requests 60 --label fp8_512

Every sweep writes its own timestamped directory plus a pareto_report.html. A per-run timeout guard (--timeout) prevents a stuck generation from blocking a sweep.

Step 3: Analyze Results

cat results/*/text_c1/profile_export_aiperf.json | python3 -m json.tool

# HTML report for one sweep (inline SVG Pareto curves, no dependencies)

Router Profiling Findings

Using vLLM's built-in enable_return_routed_experts feature, we captured the actual per-token top-8 expert IDs selected by the fused MoE kernels across all 40 layers for each dataset. This reveals how content type shapes routing behavior at the kernel level.

Methodology

The router_probe.py script uses the offline vllm.LLM API with enable_return_routed_experts=True. The fused Marlin MoE kernel captures routed expert IDs as uint8 tensors of shape (n_tokens, 40 layers, 8 experts) and returns them via CompletionOutput.routed_experts. The multi-turn probe router_probe_multiturn.py scales this to 50 sessions with up to 10 turns per session and 64 output tokens per prompt, pooling entropy across all sequences at each position index.

Correlation with Performance

The routing data explains the measured +17% reasoning decode advantage at 512-token outputs:

  1. Lower entropy = fewer active experts per token. Reasoning's concentrated routing (0.797 vs 0.799 text) means fewer expert weight pages need to be loaded from memory per decode step. On GB10's 273 GB/s unified memory, this directly reduces memory bandwidth pressure.

  3. Layer-specific concentration. Reasoning's entropy drops most sharply in layers 7-9 and 20-21. These are likely the layers where logical chain processing concentrates computation, reducing per-token MoE overhead.
  4. Fewer unique experts activated. Reasoning uses 196.9 experts/layer vs random's 215.7 — 9% fewer distinct experts means less memory fragmentation and better cache locality.
